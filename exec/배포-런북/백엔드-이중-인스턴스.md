# 백엔드 2개 인스턴스 배포 런북

이 구성은 동일한 EC2에서 `backend-app-a`와 `backend-app-b`를 실행하고 호스트 Nginx가 두 프로세스로 요청을 분산한다. 백엔드 프로세스 하나의 장애는 견딜 수 있지만 EC2, Nginx, Redis, PostgreSQL 자체는 여전히 단일 장애점이다. 무중단 배포는 목표가 아니며, 배포 중 짧은 중단과 최초 1회 재로그인을 허용한다.

## 최종 구성

| 항목 | 값 |
| --- | --- |
| A 컨테이너 | `backend-app-a`, `127.0.0.1:8081 -> 8080` |
| B 컨테이너 | `backend-app-b`, `127.0.0.1:8082 -> 8080` |
| 컨테이너 제한 | 각 `1 CPU`, `1 GiB` |
| 공유 상태 | PostgreSQL, Redis, RabbitMQ, `backend-data`, `/var/www/images` |
| HTTP 세션 | Redis `c206:session:*`, TTL 최대 1,800초 |
| 스케줄러 | Redis ShedLock, 환경별 락 이름 공간 |
| 리더보드 대기 작업 | Redis pending/processing Set |

배포 스크립트는 A가 healthy가 된 뒤 B를 시작하고 두 슬롯의 이미지와 `DEPLOY_COMMIT`이 같은지 확인한다. 어느 단계든 실패하면 새 슬롯을 모두 제거하고 배포 전 단일 컨테이너 또는 A/B 쌍을 복구한다. 롤백 성공 후에도 Jenkins 빌드는 실패로 남는다.

## 1. 배포 전 확인

EC2에서 다음을 실행한다.

```bash
free -h
nproc
df -h
docker stats --no-stream

docker exec mvp-backend-infra-redis-1 sh -c \
  'REDISCLI_AUTH="$REDIS_PASSWORD" redis-cli CONFIG GET appendonly maxmemory maxmemory-policy'

docker exec mvp-backend-infra-postgres-1 sh -c \
  'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Atc "show max_connections; select count(*) from pg_stat_activity;"'
```

진행 조건:

- Redis의 `appendonly`가 `yes`여야 한다.
- 현재처럼 Redis `maxmemory`가 0(무제한)이면 소규모 배포 동안만 허용한다. 호스트 메모리 사용률이 80% 미만이어야 하며 모니터링 후속 작업을 남긴다.
- `maxmemory-policy`는 `noeviction`을 권장한다. 세션이나 락이 메모리 압박으로 임의 제거되면 안 된다.
- 현재 연결 수와 두 백엔드의 Hikari 풀 예상치를 합쳐 PostgreSQL `max_connections`의 80% 미만이어야 한다.
- 새 Flyway 마이그레이션은 이전 이미지와 호환되어야 한다. 컬럼 삭제·이름 변경처럼 이전 이미지 롤백을 깨는 변경이 있으면 배포하지 않는다.

## 2. Nginx 설정

현재 파일은 `/etc/nginx/sites-available/default`다. 먼저 원본을 보관한다.

```bash
sudo cp --preserve=all /etc/nginx/sites-available/default \
  "/etc/nginx/sites-available/default.pre-backend-pair-$(date +%Y%m%d-%H%M%S)"
sudoedit /etc/nginx/sites-available/default
```

다음 upstream을 첫 번째 `server` 블록보다 위에 둔다. 이 파일은 Nginx `http` 컨텍스트에서 include되므로 `server` 밖에 있어야 한다.

```nginx
upstream c206_backend {
    least_conn;
    server 127.0.0.1:8081 max_fails=1 fail_timeout=10s;
    server 127.0.0.1:8082 max_fails=1 fail_timeout=10s;
    keepalive 32;
}
```

기존 TLS `server` 안의 Swagger와 `/api/` location을 아래 내용으로 교체한다. Swagger Basic Auth 파일과 문구는 기존 값 그대로 유지한다. `/`, `/ops/`, `/jenkins/`, `/images/`, 인증서 설정과 `location = /api { return 301 /api/; }`는 변경하지 않는다.

```nginx
location ^~ /api/swagger-ui/ {
    auth_basic "API Documentation";
    auth_basic_user_file /etc/nginx/.htpasswd-api-docs;

    proxy_pass http://c206_backend/swagger-ui/;
    proxy_http_version 1.1;
    proxy_set_header Connection "";
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}

location = /api/v3/api-docs {
    auth_basic "API Documentation";
    auth_basic_user_file /etc/nginx/.htpasswd-api-docs;

    proxy_pass http://c206_backend/v3/api-docs;
    proxy_http_version 1.1;
    proxy_set_header Connection "";
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto $scheme;
}

location = /api/v3/api-docs/swagger-config {
    auth_basic "API Documentation";
    auth_basic_user_file /etc/nginx/.htpasswd-api-docs;

    proxy_pass http://c206_backend/v3/api-docs/swagger-config;
    proxy_http_version 1.1;
    proxy_set_header Connection "";
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto $scheme;
}

location /api/ {
    proxy_pass http://c206_backend;
    proxy_http_version 1.1;
    proxy_set_header Connection "";

    client_max_body_size 6m;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;

    proxy_buffering off;
    proxy_connect_timeout 10s;
    proxy_send_timeout 90s;
    proxy_read_timeout 90s;
    proxy_next_upstream error timeout http_502 http_503 http_504;
    proxy_next_upstream_tries 2;
}
```

일반 `/api/`의 `proxy_pass`에는 의도적으로 뒤쪽 `/`가 없다. 요청 URI의 `/api/...`를 그대로 백엔드에 전달한다. 반대로 Swagger 세 경로는 외부 `/api/...`를 백엔드의 `/swagger-ui/...`, `/v3/api-docs...`로 바꾸기 위해 위 매핑을 사용한다.

설정을 검사한 뒤 적용한다.

```bash
sudo nginx -t
sudo systemctl reload nginx
sudo systemctl status nginx --no-pager
```

`nginx -t`가 실패하면 절대로 reload하지 않는다.

## 3. 백엔드 배포

Jenkins 배포는 `scripts/deploy-backend.sh`를 호출한다. 수동 검증 시에도 동일한 인자 순서를 사용한다.

```bash
./scripts/deploy-backend.sh \
  develop \
  c206-backend:develop-<commit8> \
  <commit8> \
  <runtime-env-file> \
  <diagnostics-directory>
```

`develop`은 Spring `develop`, `main`은 Spring `prod` 프로필로 매핑된다. 기존 이미지가 단일 `backend-app`이면 최초 배포에서 이를 A/B 쌍으로 전환한다. 기존 A/B 중 하나만 있거나 두 슬롯의 이미지·커밋이 다르면 컨테이너를 제거하기 전에 배포가 실패한다.

## 4. 배포 직후 확인

```bash
curl -fsS http://127.0.0.1:8081/actuator/health
curl -fsS http://127.0.0.1:8082/actuator/health

docker inspect --format '{{.Name}} {{.Config.Image}} {{range .Config.Env}}{{println .}}{{end}}' \
  backend-app-a backend-app-b | \
  grep -E '/backend-app-|DEPLOY_COMMIT=|SPRING_PROFILES_ACTIVE='

docker stats --no-stream backend-app-a backend-app-b
docker ps --filter name=backend-app --format 'table {{.Names}}\t{{.Status}}\t{{.Ports}}'
```

두 health 응답은 모두 `UP`, 이미지·커밋·프로필은 동일해야 한다. 각 컨테이너는 1 GiB 제한 안에서 안정적이어야 하며 재시작이 반복되면 배포를 중단한다. 실제 트래픽에서 EC2 CPU와 메모리가 지속적으로 80%를 넘으면 한 호스트 2개 구성을 유지하지 않는다.

로그 확인:

```bash
for container in backend-app-a backend-app-b; do
  echo "===== $container ====="
  docker logs --tail 200 "$container"
done
```

## 5. 세션·CSRF·장애 전환 인수 테스트

최초 전환에서는 기존 컨테이너 메모리 세션이 Redis로 이전되지 않으므로 사용자는 1회 다시 로그인해야 한다. 이후에는 두 슬롯이 같은 Redis 세션을 사용한다.

1. 브라우저에서 일반 로그인과 OAuth 로그인을 확인한다.
2. 개발자 도구에서 `JSESSIONID`와 `XSRF-TOKEN` 쿠키를 확인한다.
3. `X-XSRF-TOKEN` 헤더를 사용하는 쓰기 요청을 한 번 성공시킨다.
4. 아래 순서로 슬롯을 하나씩 중지한다.

```bash
docker stop backend-app-a
curl -fsS http://127.0.0.1:8082/actuator/health
# 열린 브라우저에서 /api/v1/users/me 새로고침과 CSRF 보호 쓰기 요청 수행

docker start backend-app-a
until curl -fsS http://127.0.0.1:8081/actuator/health; do sleep 2; done

docker stop backend-app-b
curl -fsS http://127.0.0.1:8081/actuator/health
# 같은 인증 읽기/쓰기를 반복

docker start backend-app-b
until curl -fsS http://127.0.0.1:8082/actuator/health; do sleep 2; done
```

기대 결과:

- 슬롯 하나를 중지해도 재로그인이 필요 없다.
- 새 CSRF 토큰을 사용한 쓰기 요청에 403이 발생하지 않는다.
- OAuth 추가 가입 대기 상태도 슬롯 중지 후 유지된다.
- EventSource/SSE는 한 번 재연결되고 다시 이벤트를 받는다.
- 두 컨테이너가 다시 healthy 상태가 된다.

Redis와 RabbitMQ 확인:

```bash
docker exec mvp-backend-infra-redis-1 sh -c \
  'REDISCLI_AUTH="$REDIS_PASSWORD" redis-cli --scan --pattern "c206:session:*" | head'

docker exec mvp-backend-infra-redis-1 sh -c '
  export REDISCLI_AUTH="$REDIS_PASSWORD"
  key="$(redis-cli --scan --pattern "c206:session:sessions:*" | head -n 1)"
  test -n "$key" && redis-cli TTL "$key"
'

docker exec mvp-backend-infra-redis-1 sh -c \
  'REDISCLI_AUTH="$REDIS_PASSWORD" redis-cli --scan --pattern "*bossLeaderboardBroadcast*"'

docker exec mvp-backend-infra-rabbitmq-1 rabbitmqctl list_queues name consumers
```

세션 TTL은 0보다 크고 1,800 이하여야 한다. ShedLock 키는 실행 후 빠르게 만료되므로 스캔 결과가 비어 있는 것만으로 실패로 판단하지 않는다. 자동화된 두 LockProvider 통합 테스트가 결정적 검증이다. 두 백엔드가 healthy일 때 RabbitMQ 결과 큐에는 consumer가 연결되어 있어야 한다.

## 6. 롤백

백엔드 배포 실패 시 스크립트가 이전 topology를 자동 복원한다. 롤백이 성공해도 새 배포 명령은 0이 아닌 종료 코드를 반환한다. 수동 재배포가 필요하면 보존된 이전 이미지 태그로 같은 스크립트를 다시 실행한다.

Nginx 설정 롤백은 먼저 백업 목록을 보고 복원 대상을 사람이 확인한다.

```bash
ls -1t /etc/nginx/sites-available/default.pre-backend-pair-* | head -n 1
```

출력된 정확한 경로를 확인한 뒤 아래 `<확인한-백업-경로>`에 직접 넣는다. 백업 선택과 덮어쓰기를 한 명령으로 자동화하지 않는다.

```bash
sudo cp --preserve=all <확인한-백업-경로> /etc/nginx/sites-available/default
sudo nginx -t
sudo systemctl reload nginx
sudo systemctl status nginx --no-pager
```

## 7. 배포 중단 조건

- 요구사항이 동일 EC2 프로세스 장애 대응이 아니라 호스트/AZ 고가용성으로 바뀌었다.
- Redis AOF가 꺼져 있거나 Redis가 재시작·eviction·메모리 압박을 보인다.
- 가장 긴 스케줄러 실행 시간이 해당 `lockAtMostFor`의 50% 이상이다.
- 반복 실행에 안전하지 않은 스케줄러 부작용이 발견된다.
- PostgreSQL 예상 연결 수가 `max_connections`의 80% 이상이다.
- A/B 이미지, 커밋 또는 프로필이 다르다.
- Nginx 단일 슬롯 중지 테스트가 실패하거나 `proxy_next_upstream`에 `non_idempotent`가 추가되어 있다.
- 이전 이미지가 새 Flyway 스키마와 호환되지 않는다.
- 두 컨테이너가 OOM 또는 재시작 루프를 보이거나 호스트 CPU/메모리가 지속적으로 80%를 넘는다.

이 구성은 EC2 한 대의 장애를 해결하지 않는다. 그 수준의 가용성이 필요하면 별도 EC2/AZ, 외부 로드밸런서, 관리형 데이터 계층으로 확장해야 한다.
