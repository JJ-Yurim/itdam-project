# 프론트엔드 배포 절차

프론트엔드는 백엔드·AI 서비스와 동일한 구조로 배포한다. Jenkins가 EC2 호스트에서 이미지를 빌드하고 컨테이너를 교체하며, 공개 트래픽은 호스트 nginx가 받는다.

## 구성

| 항목 | 값 |
| --- | --- |
| Jenkinsfile | `Jenkinsfile.frontend` |
| Dockerfile | `frontend/Dockerfile` (멀티스테이지: `deps` → `verify` / `build` → `runtime`) |
| 컨테이너 nginx 설정 | `frontend/nginx.conf` |
| 배포 스크립트 | `scripts/deploy-frontend.sh` |
| 배포 이미지 | `c206-frontend:<branch>-<commit8>` (최근 3개 보존) |
| 검증 이미지 | `c206-frontend-verify:<branch>-<commit8>` (검증 후 삭제) |
| 컨테이너 | `frontend-app` |
| 바인딩 | `127.0.0.1:3000` → 컨테이너 `80` |
| 공개 URL | `https://app.example.com/` |

`VITE_API_BASE_URL`은 Vite가 빌드 타임에 인라인하므로 런타임 환경 변수로 바꿀 수 없다. Jenkins가 `--build-arg VITE_API_BASE_URL=/api`로 주입한다. 프론트엔드와 API가 같은 도메인이므로 상대 경로를 사용하며, 별도 CORS 설정과 `FRONTEND_ALLOWED_ORIGINS`는 필요하지 않다.

프론트엔드는 비밀값을 사용하지 않으므로 Jenkins Credentials 바인딩이 없다. 값이 필요해지면 백엔드와 같은 `umask 077` 임시 환경 파일 방식을 따르되, 빌드 타임에 인라인되는 값은 브라우저에 노출되므로 비밀값으로 취급하지 않는다.

## 1. 호스트 nginx 라우트 추가

호스트에 apt로 설치된 nginx의 기존 server 블록(`/etc/nginx/sites-available/` 아래, TLS와 `/api/` 프록시가 이미 설정된 파일)에 `/` 라우트를 추가한다. 기존 `/api/`와 Swagger Basic Auth 블록은 그대로 둔다.

```nginx
    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
```

`location /`가 이미 있으면 새로 추가하지 말고 그 블록의 내용을 위 프록시로 교체한다. nginx는 `/api/`처럼 더 긴 prefix를 우선 매칭하므로 API 경로는 영향을 받지 않는다.

적용:

```bash
sudo nginx -t && sudo systemctl reload nginx
```

포트 3000이 이미 사용 중이면 `scripts/deploy-frontend.sh`의 `host_port`와 위 `proxy_pass`를 같은 값으로 함께 바꾼다.

```bash
sudo ss -ltnp | grep 3000
```

## 2. Jenkins Job 생성

백엔드·AI 서비스와 같은 방식으로 별도 Pipeline Job을 만든다.

1. New Item → Pipeline (이름 예: `c206-frontend-develop`)
2. Pipeline → Definition: `Pipeline script from SCM`
3. SCM: Git, 저장소와 자격 증명은 기존 Job과 동일
4. Branches to build: `*/develop`
5. Script Path: `Jenkinsfile.frontend`
6. Build Triggers: 기존 Job과 동일한 방식(GitLab webhook 또는 SCM 폴링)

파이프라인은 `main`, `develop` 외 브랜치에서는 실패한다. `frontend/**`, `scripts/deploy-frontend.sh`, `Jenkinsfile.frontend`가 변경되지 않은 빌드는 스킵되며, 첫 빌드와 `FORCE_DEPLOY` 파라미터는 예외다.

`changeset`은 직전 빌드 이후의 커밋만 본다. 프론트엔드 변경이 든 빌드가 Deploy 전에 실패하면 그 변경은 다음 빌드의 `changeset`에 없어 스킵되고, Job은 초록불인데 배포본만 develop보다 뒤처지게 된다. 이를 막기 위해 실행 중인 `frontend-app`의 `DEPLOY_COMMIT`과 현재 커밋을 비교하는 조건이 함께 걸려 있다. 두 값이 다르면 변경 경로와 무관하게 배포가 진행된다.

Job 파라미터는 첫 빌드가 끝난 뒤에 Jenkins UI에 나타나므로, 강제 배포는 두 번째 빌드부터 `Build with Parameters`에서 `FORCE_DEPLOY`를 켜서 실행한다.

## 3. 파이프라인 단계

1. **Frontend Verify** — `--target verify`로 빌드한 컨테이너에서 `pnpm lint`, `pnpm typecheck`, `pnpm test`를 실행하고 JUnit XML을 `docker cp`로 `frontend/build/test-results/`에 꺼낸다. Jenkins 호스트에 Node나 pnpm을 설치하지 않기 위한 구성이며, 네트워크 없이(`--network none`) 실행한다. 검증 이미지(`c206-frontend-verify:<branch>-<commit8>`)는 스테이지가 끝나면 삭제한다.
2. **Build Frontend Image** — `runtime` 스테이지까지 빌드한다. `verify`와 `deps` 레이어를 공유하므로 의존성 설치는 재사용된다. `pnpm build`가 `tsc -b`를 포함하므로 타입 오류는 이미지 빌드에서도 실패로 이어진다.
3. **Deploy Frontend** — 기존 `frontend-app`을 제거하고 신규 컨테이너를 기동한 뒤 Docker healthcheck와 호스트 포트 응답을 함께 확인한다. 실패하면 로그 200줄을 남기고 이전 이미지로 롤백하며, 롤백이 성공해도 빌드는 실패로 처리한다. 배포에 성공하면 최근 `FRONTEND_IMAGE_KEEP`(기본 3)개를 제외한 배포 이미지를 삭제한다.

HEALTHCHECK은 컨테이너 **내부**에서 실행되므로 `-p 127.0.0.1:3000:80` 포트 게시가 실제로 동작하는지는 증명하지 못한다. 배포 스크립트가 호스트 포트로 `/healthz`를 한 번 더 확인하는 이유다.

## Jenkins가 컨테이너라는 전제

이 프로젝트의 Jenkins는 EC2 위 컨테이너에서 돌고 Docker 데몬은 호스트 것을 공유한다. 파이프라인과 배포 스크립트는 두 가지 함정을 우회하도록 작성되어 있다.

- **`-v $WORKSPACE/...` 볼륨 마운트는 쓰지 않는다.** 마운트 경로는 Docker 데몬(호스트) 기준으로 해석되므로, Jenkins 컨테이너 내부 경로인 워크스페이스에는 파일이 도착하지 않는다. 테스트 리포트는 `docker cp`로 컨테이너 파일시스템에서 직접 꺼낸다.
- **호스트 루프백은 직접 curl로 접근할 수 없다.** 스크립트의 127.0.0.1은 Jenkins 컨테이너의 루프백이다. 호스트 게시 포트 확인은 `docker run --network host` 헬퍼 컨테이너로 수행하며, 별도 이미지를 받지 않도록 wget(busybox)이 포함된 배포 이미지 자신을 재사용한다.

`buildDiscarder`는 Jenkins 빌드 기록만 지우고 Docker 이미지는 남긴다. 위 두 정리 단계가 없으면 빌드마다 이미지가 쌓여 결국 디스크 부족으로 배포가 실패한다. 실행 중인 컨테이너가 쓰는 이미지는 삭제되지 않는다.

## 4. 정적 파일 서빙 규칙

`frontend/nginx.conf`는 컨테이너 내부 nginx 설정이다.

- `createBrowserRouter`를 사용하므로 `/workshop`, `/library` 같은 클라이언트 라우트는 `try_files ... /index.html`로 폴백한다.
- 확장자가 명확한 요청(`.js`, `.css`, `.svg` 등)은 폴백에서 제외해 없으면 404가 난다. 폴백이 전 경로에 걸리면 자산 누락이 200으로 가려지고, 브라우저가 HTML을 JS·이미지로 파싱하며 원인을 알기 어려운 오류가 난다.
- `/assets/`는 Vite가 파일명에 콘텐츠 해시를 넣으므로 `immutable`로 1년 캐시한다. 정규식 location이 prefix location보다 우선하므로 `^~`로 우선순위를 고정해 위 확장자 규칙에 덮이지 않게 한다.
- `index.html`은 해시가 없어 `no-cache`로 매번 재검증한다. 배포 직후 새 자산이 즉시 반영되게 하는 조건이다.
- `mockServiceWorker.js`는 `frontend/public/`에 있어 `dist`에 포함되지만 런타임 이미지에서 삭제한다. 프로덕션 빌드에는 등록 경로가 없지만 서빙할 이유도 없다.
- `/healthz`는 컨테이너 HEALTHCHECK과 배포 스크립트의 호스트 확인용이며 액세스 로그를 남기지 않는다.

## 로컬에서 배포 이미지 확인

```bash
MSYS_NO_PATHCONV=1 docker build --build-arg VITE_API_BASE_URL=/api -t c206-frontend:local .
docker run --rm -p 127.0.0.1:3000:80 c206-frontend:local
```

Git Bash는 `--build-arg`의 `/api`를 Windows 경로(`C:/Program Files/Git/api`)로 변환하므로 `MSYS_NO_PATHCONV=1`이 필요하다. 이 값이 번들에 그대로 인라인되면 배포된 앱의 모든 API 호출이 깨지므로 로컬 확인 시 결과를 검증한다. PowerShell과 Jenkins(Linux `sh`)에서는 변환이 일어나지 않는다.

```bash
curl -s http://127.0.0.1:3000/ | grep -o 'assets/index-[^"]*\.js'
curl -s http://127.0.0.1:3000/assets/index-<hash>.js | grep -o 'baseURL:.\{0,10\}'
```

## 장애 확인

```bash
docker ps --filter name=frontend-app
docker logs --tail 200 frontend-app
curl -fsS http://127.0.0.1:3000/healthz
curl -fsS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:3000/workshop
```

마지막 명령이 `200`이면 SPA 폴백이 동작한다. 컨테이너는 정상인데 브라우저에서 404가 보이면 호스트 nginx의 `location /`를 먼저 확인한다.

배포된 커밋 확인:

```bash
docker inspect --format '{{range .Config.Env}}{{println .}}{{end}}' frontend-app | grep DEPLOY_
```

## 수동 롤백

이전 이미지 태그로 스크립트를 직접 실행한다.

```bash
docker images c206-frontend
./scripts/deploy-frontend.sh develop c206-frontend:develop-<commit8> <commit8>
```

## 보스 페이즈 이미지 정적 제공

페이즈 이미지는 프론트 컨테이너가 아니라 EC2 호스트 Nginx가 직접 반환한다. 호스트 디렉터리는
`/var/www/images`이며 백엔드 컨테이너의 `/app/data/images`에 bind mount된다. 기존
`backend-data:/app/data` 볼륨은 유지하고 더 좁은 이미지 mount를 뒤에 둔다.

```nginx
location ^~ /images/ {
    alias /var/www/images/;
    add_header Cache-Control "public, max-age=31536000, immutable";
    add_header X-Content-Type-Options "nosniff" always;
}
```

`/api/`와 Swagger 프록시는 단일 포트가 아니라 A/B upstream을 사용한다. 정확한 설정과 적용 순서는 [백엔드 2개 인스턴스 배포 런북](백엔드-이중-인스턴스.md)을 따른다. `/images/` location은 위 설정을 그대로 유지한다.

배포 스크립트는 대상 이미지의 `spring` UID/GID를 조회해 `/var/www/images` 소유권을 맞추고,
`infra/assets/boss-phase-placeholder.svg`를 `system/boss-phase-placeholder.svg`로 복사한다.
디렉터리는 755, 플레이스홀더는 644를 사용한다. 관리자 업로드에는 SVG를 계속 허용하지 않는다.

```bash
sudo nginx -t
sudo systemctl reload nginx
curl -I https://app.example.com/images/system/boss-phase-placeholder.svg
sudo tar -C /var/www -czf /var/backups/boss-images-$(date +%F).tgz images
```
